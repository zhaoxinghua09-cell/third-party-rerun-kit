# 凭证暴露事件记录（2026-11-26）

## 事实

在测试外部模型通道是否可用于 E1 独立审查时，我对保险库条目 `hunyuan_api_key` 做了取用与请求测试。
该条目内容是"secret_id + sk-…"两行合并存储，而我把整段值直接拼进 `Authorization: Bearer …` 请求头，
请求在本地抛出 `ValueError: Invalid header value`，异常消息把请求头的完整值（含 secret_id 与 sk）写进了 stdout。
因此这两段明文进入了本次会话的工具输出与日志。

## 范围

- 仅本机会话日志（客户端本地），未写入任何仓库、未推送到远端、未进入任何提交。
- 同批测试中 `dashscope_api_key` 只返回 HTTP 403，未回显内容；该条不受本次事件影响。

## 已做的处置

- 立即停止继续打印该条目内容；后续测试只取以 `sk-` 开头的行，且不再打印任何前缀。
- 未使用该明文做任何实际操作（后续以 `sk-` 行测试返回 401 Unauthorized，说明该 key 本身也不可用）。
- 本文件只记录条目名与事故形态，**不复制、不复述任何密钥字符**。

## 建议（需你本人决定）

1. 若该混元 key 仍在其他系统使用，请到控制台轮换；本机保险库条目 `hunyuan_api_key` 同步更新。
2. 这类"多行合并存储的凭证"在拼请求头时容易被整段带出；建议在保险库条目里拆分字段（id / sk 分开存），
   或在使用侧强制只取单行。
3. 本次事件属于"本地日志暴露、未外发"，按既有习惯可记为 EXPOSED_LOCAL，不必按外发事故升级处理。

## 与 E1 的关系

这次测试的结论是负面的：**两条外部模型通道都不可用**（dashscope 403、hunyuan 401）。
因此 E1"外部 AI 独立审查"在本机仍为 FAIL/未取证，不能用"试过了"冒充"审过了"。
