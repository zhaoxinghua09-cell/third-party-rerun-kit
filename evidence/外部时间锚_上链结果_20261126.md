## 二、没有比特币节点，怎么做验证（新增 `ots_light_verify.py`）

`ots verify` 需要本地区块头链（本机没有 bitcoind，报 `Could not connect to Bitcoin node`）。所以写了一个轻验证：

1. 从 `.ots` 取出比特币 attestation 的高度；
2. 向 **mempool.space** 与 **blockstream.info** 两家独立浏览器查同一高度的区块哈希，**两家必须一致**；
3. 取该区块 80 字节区块头，交给库的 `verify_against_blockheader(msg, header)` 做 **Merkle 路径 + 区块头绑定**校验（这是密码学校验，不是"看一眼哈希对不对"）；
4. 不做 PoW / 难度校验——那要区块头链。

实跑结果（两份证明各 2 条 attestation）：

```
高度 977531  绑定校验=True（merkle 字节序=raw）
高度 977532  绑定校验=True
比特币 attestation 通过校验: 2；失败/不可信: 0；日历 attestation: 4
LIGHT_VERIFY = PASS
```

## 三、现在能说什么

**能说**：这把公钥（以及那份声明它已公开的 JSON）的 SHA-256，已经被绑定进比特币区块 977531 与 977532 的 Merkle 根里；任何拿到这两份 `.ots` + 原始文件的人，都能独立复算到区块头，不依赖我们、也不依赖任何一家日历。

**不能说**：
- 不说"完整验证通过"——完整验证含 PoW，需区块头链（`ots verify`）；
- 不说"这是我做的"——时间锚只证明"某时点前已存在"，不证明持有人身份；
- 不说"日历可靠"——`btc.calendar.catallaxy.com` 今天就回了 `Not found`，是另外两家给了 attestation；这正是多日历冗余的意义。

## 四、三层锚的现状

| 层 | 机制 | 状态 |
|---|---|---|
| L1 账号锚 | GitHub commit 钉公钥（`anchor.json`） | 已跑通，A10 实测拦下换钥 |
| L2 时间锚 | OpenTimestamps → 比特币 977531/977532 | **已上链、已做绑定校验（LIGHT_VERIFY PASS）** |
| L3 域名锚 | DANE/TLSA + DNSSEC | 无域名，未做 |

L1 + L2 合起来，性质从"我们说了算"变成"两件外部可查的事对上号"：公钥在某次提交里首次公开，且该公开动作被钉在某个比特币高度之前。
