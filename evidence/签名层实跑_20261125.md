# 签名层实跑记录 · 2026-11-25

## 两条路，一条通一条不通

| 路线 | 结果 | 数字 |
|---|---|---|
| Sigstore / cosign（官方二进制） | **未通** | release `v3.1.5` 官方包 **191,166,976 B**，本机实得 **32,505,856 B**（**17%**），MZ 头不完整、不可执行 |
| Ed25519 自包含签名（`cryptography`） | **通** | 签名 → 独立验签 → 复跑器 20/20 PASS，exit 0；A9（换公钥）验签失败，exit 3 |

cosign 失败的形态值得记：第一次用 `Invoke-WebRequest` 拿到 55,639,107 B，脚本以"大于 1MB 就算成功"为判据，**报了成功**——但 PE 头是坏的。这正是本轮反复出现的同一个病：**用弱判据宣布成功**。后来改成先读官方 `size`、再比对下载后实际大小，才把"截断"这件事抓出来（`D:\Workbuddy\tools\get_cosign.py`）。下载仍未完成，原因是本机到 GitHub release 的吞吐被限（约 2.4 MB/分钟）。

## Ed25519 这一路做了什么

- `ed25519_sign.py`：生成密钥（私钥留本地 `keys\ed25519_private.pem`，不入库），对 `outputs/result.txt` 签名，写 `attest/result.sig.json`（含 `target_sha256`、`public_key_b64`、`sig_b64`）。
- 复跑器新增验签：先比"被签字节的哈希"（防"签名对但文件换了"），再用包内公钥验签。
- 结果：`demo_pkg_signed` **20/20 PASS**，其中
  - `signature（被签字节未被改动）` PASS
  - `signature（Ed25519 验签）` PASS

## 这一层的能力边界（必须跟着签名一起说）

签名解决的是"**这份字节被这把私钥签过**"，不解决"**这把私钥属于谁**"。

- 攻击者完全可以自带密钥、自带签名、自带公钥，造一个 100% 自洽的包 —— 我们的工具会判 PASS，因为在这个封闭世界里它确实成立。
- 要破这一层，必须有**外部信任锚**：域名下的 well-known 公钥、组织目录、Sigstore 的透明日志、或别人已经认识的你的指纹。我们目前**没有**这个锚。
- 所以对外只能说：包是自洽的、签名在包内可验；**不能说"这是我做的"**。

## 复跑的人在两种环境下会得到两种结论（这是设计，不是 bug）

| 环境 | 结论 | 退出码 |
|---|---|---|
| 装了 `cryptography` | PASS（验签通过） | 0 |
| 空 venv，无 `cryptography` | **INCOMPLETE**（验不了，不是通过） | 4 |

同包不同判，恰恰说明第 4 条不是装饰：**没能力验的时候，工具必须承认没能力**，而不是默认放行。
