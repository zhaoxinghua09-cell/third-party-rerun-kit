# 第三方复跑工具包（rerun kit）

用途：当有人请你"以第二个独立方身份复跑一段验证链"时，用这套工具跑，**不跑对方代码**、只核对对方声明。

## 为什么默认不执行对方脚本

拿到陌生代码就在自己机器上跑，等于把机器交出去（对方可以是善意的，也可以是被人塞了东西的）。所以默认走**声明式校验**：对方在 `manifest.json` 里声明"这些文件的哈希是这些、这条链的期望值是这些"，我们只重算、只比对。要跑脚本必须显式 `--run-steps`，且逐条打印。

## 文件

| 文件 | 作用 |
|---|---|
| `verify_chain.py` | 复跑器。参数 `--pkg <目录>`，`--json <输出>`。退出码 0 全过 / 3 有不过 / 2 manifest 坏 |
| `make_demo_pkg.py` | 造合成演示包 `demo_pkg/`（不含任何真实数据） |
| `redteam.py` | 对复跑器本身做红队，6 种攻击必须全部被拦 |
| `demo_run.json` / `outsider_run.json` | 两次独立运行的机器可读结果 |

## 复跑器查什么（14 项）

1. `structure`：steps 不能为空（没有链就不许 PASS）
2. `coverage`：manifest 里声明的每个文件都必须被某条 step 引用（防"声明 12 个文件、实际只校验 3 个"）
3. `coverage`：每个期望输出都必须被链绑定（防结论与证据脱钩）
4. `hash-length`：全部期望值必须 64 位 sha256（短前缀可暴力碰撞）
5. `white-list`：包内出现未声明文件即 FAIL（防夹带）
6–8. 逐文件哈希
9–13. 逐条链步骤（`sha256_file` / `spine_hash`）
14. 期望输出哈希

## 三种用法

```powershell
python make_demo_pkg.py                     # 造演示包
python verify_chain.py --pkg demo_pkg --json demo_run.json
python redteam.py                           # 对复跑器自己红队
```

对方包到手后：`python verify_chain.py --pkg <他的包> --json <他的名字>_run.json`

manifest 格式见 `verify_chain.py` 顶部注释。

## 已实跑的结论（2026-11-25）

- 基线（未篡改）：14/14 PASS，exit 0
- 红队 6 攻：6/6 被拦，exit 3
- 干净环境（空 venv 仅 pip、代理指向未开放端口、无任何密钥）：与主环境**完全一致**（14/14 + 6/6）
- 首次红队实跑抓到过 1 个真漏洞：抽走 `steps` 后旧版仍判 PASS。已改为"链为空即不合格"，并把 demo 包补到全覆盖 —— 记录在 `红队与修法_20261125.md`

## 边界（写清楚，不要含糊）

- 这套工具只能证明"**在给定包上，声明与文件一致**"。它不能证明对方的研究结论成立，也不能证明包本身没被设计成自洽的假账（`A4 自证循环` 那次攻击就是展示这个边界的：攻击者如果能同时改文件、改期望值、改 spine，复跑器只能报不一致，无法替你判断谁对）。
- 所以对外只能声明"复现性"，不能声明"证实"。
